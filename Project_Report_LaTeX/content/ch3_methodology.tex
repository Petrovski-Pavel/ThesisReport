\chapter{Methodology}
\label{ch:methodology}

This chapter describes the methodology used to develop a computer-vision pipeline
for detecting and interpreting elevator buttons in hospital environments. The
project is conducted with the objective of building a scalable and
deployment-oriented perception system that can be iteratively improved across
different hospital settings and reused within a robot fleet.

\section{Overview of the proposed perception workflow}

The proposed methodology focuses on instance-level localization of interaction
elements such as elevator buttons and control panels. Instance segmentation is used
to detect individual button instances at pixel level, allowing precise localization
and separation of closely spaced elements. This capability provides the basis for
subsequent interpretation of button functions and autonomous interaction.

The methodology is designed to support an iterative training and deployment
workflow. An initial base model is deployed on the robot, where it performs
interaction-point perception and collects visual data during operation. Selected
data can be transferred to an offboard system, where annotations may be reviewed,
corrected, or extended before retraining the perception models. The updated models
are then redeployed to the robot and become the new default for continued operation.

In the implemented improvement loop, not every observed frame is exported for
later review. Instead, the \gls{adc} applies quality gates and stores only 
frames that contain accepted button targets satisfying detector and \gls{ocr} confidence thresholds,
 and compliance with the additional export
constraints described later in this chapter, such as image-quality, stability,
and de-duplication checks. The offboard review stage therefore starts from a
filtered set of high-value samples rather than from the full camera stream,
which makes the improvement loop in Figure~\ref{fig:scalable_workflow} an
implemented data-collection process rather than only a conceptual workflow diagram.

This workflow enables gradual adaptation to new hospital environments and allows
knowledge acquired in one deployment to be reused and refined in subsequent
deployments. The target end-to-end training and deployment process developed in this
project is illustrated in Figure~\ref{fig:scalable_workflow}. Figure~\ref{fig:scalable_workflow}
therefore serves as a combined workflow-and-architecture overview: it links the
source dataset, annotation and training stages, deployment on the robot, and the
feedback path introduced by the \gls{adc}. The training-side annotation
architecture is detailed later in Figure~\ref{fig:annotation_workflow}, and the
deployed runtime architecture is detailed in Figure~\ref{fig:ros2_runtime_architecture}.

The following sections describe each stage of the methodology in detail, beginning
with dataset selection and preparation.

\section{Dataset selection and preparation}
\label{sec:dataset_selection}

Within the overall workflow-and-architecture overview shown in
Figure~\ref{fig:scalable_workflow}, this section covers the preparation steps
that precede the first model-training phase. Before any segmentation or recognition model can be trained, the source
dataset must be selected, split, reformatted, and extended where needed for the
later deployment setting.

This project uses the elevator-panel dataset released by \citet{liu2021elevator}.
For this thesis, the working dataset comprised approximately 2000 images, split
into 1122 training images, 281 validation images, and 602 held-out test images.
The test split was reserved for final evaluation only.

The original dataset provided \gls{xml} annotations with bounding boxes and textual
labels, but no instance masks. To support instance segmentation, the images were
re-annotated in a semi-automatic \gls{cvat} workflow using a \gls{maskrcnn}
pre-annotation model, as described in Section~\ref{sec:annotation_strategy}. The resulting annotations
were stored in \gls{coco}-style \gls{json} and then converted to the label format
required by \gls{yolo}-based segmentation training.

In the later deployment-oriented adaptation stage, the dataset was extended with
46 additional images collected in Han Building R29, the pilot
environment for robot deployment testing. These images were added only after the
baseline and hyperparameter tuning stages, so that the initial \gls{yolo}
experiments remained directly comparable with the original benchmark setting.
\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.4\textwidth]
    {figures/methodology/71.jpg}
    \caption{Example raw image from the dataset.}
    \label{fig:example_raw_image}
\end{figure}

The resulting dataset structure provides a consistent and reusable foundation for
annotation, model training, and evaluation, as described in the following sections.

In addition to the instance-segmentation datasets, a recognition dataset for the
semantic interpretation stage was derived from the same annotated source images.
For this purpose, each annotated button instance was cropped from the original
image using its existing bounding-box annotation, with an additional contextual
padding of 15\% of the box width and height. This produced a button-centered crop
dataset for \gls{ocr} fine-tuning without requiring any additional manual image
collection.

The \gls{ocr} dataset builder grouped crops by source image before creating a fixed
80/20 train/validation split with a deterministic random seed. As a result, all
button crops originating from one panel image were placed either in the training
set or in the validation set, but never in both. This prevents information
leakage caused by highly similar button appearances within the same elevator
panel. The held-out \gls{ocr} test set was generated directly from the original test
images and their annotations.

Several \gls{ocr} dataset variants were explored during development. The final variant
used for the main recognition experiments removed labels named exactly
\texttt{text} and labels starting with the prefix \texttt{text\_}. These labels do
not encode the actual button content, but merely indicate the presence of
unspecified free text. Retaining them caused the recognizer to over-predict
generic ``TEXT''-like outputs and reduced generalization to unseen textual button
content. The final \gls{ocr} dataset, contained 11{,}953 training
crops, 2{,}973 validation crops, and 6{,}861 held-out test crops.

\section{Annotation strategy and workflow}
\label{sec:annotation_strategy}

Instance-level ground truth was created using a semi-automatic workflow that
combines model-based pre-annotation with manual verification. This strategy was
used to efficiently generate high-quality instance segmentation annotations while
maintaining consistency across the dataset.

Annotations were created in \gls{cvat} \citep{cvat2020}, deployed locally using Docker
\citep{merkel2014docker} within a \gls{wsl}-based Linux environment on a Windows host. Automatic annotation was enabled through \gls{cvat}--Nuclio integration, where the model
was deployed as a Nuclio serverless function \citep{nuclio}. The instance
segmentation model used for automatic annotation was \gls{maskrcnn} \citep{he2017maskrcnn}.

During automatic annotation, \gls{cvat} sends task images to the Nuclio function, where
\gls{maskrcnn} predicts binary masks for each detected button instance. These masks
are converted into polygon shapes within the Nuclio function and returned to \gls{cvat}
as annotation data. The overall workflow used in this project is shown in
Figure~\ref{fig:annotation_workflow}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=1.15\textwidth]{figures/methodology/docker_cvat_nuclio_setup.png}
    \caption{Semi-automatic annotation workflow on a Windows host using \gls{wsl},
    Docker, \gls{cvat}, and Nuclio.}
    \label{fig:annotation_workflow}
\end{figure}

To support iterative improvement, the dataset was annotated in batches of
approximately 150 images. After each three batches, Mask R-CNN annotation-support model was retrained using the
newly annotated data and reused for subsequent annotation rounds. Model checkpoints
were created after approximately 90, 449, and 900 annotated images, followed by a
final checkpoint trained on the full 1400-image training split. This enabled
progressively improved pre-annotations and reduced manual correction effort. A
quantitative comparison of these annotation-support checkpoints on the held-out
test set is provided in Appendix~\ref{app:maskrcnn_checkpoints}.

All automatically generated annotations were also manually reviewed and corrected
when needed to ensure accurate instance boundaries, correct separation of
adjacent buttons, and consistent labeling across both the training and test
sets. This manual verification step was retained because fully automatic
acceptance would have been faster, but it would also have propagated model
mistakes into the training data, especially for touching buttons, incomplete or missed
masks. A fully manual workflow, by
contrast, would have offered maximum control at substantially much higher annotation
time and lower scalability. The chosen hybrid approach therefore balanced
annotation efficiency with dataset quality.

\section{Dataset quality assessment}

A brief dataset quality assessment was performed before the main training
experiments to check whether the dataset contained a substantial subset of
clearly unusable images.

For each training image, two basic image-level indicators were computed:
\begin{itemize}
    \item a blur indicator based on the variance of the Laplacian, used only as
    a relative sharpness measure.
    \item the mean grayscale intensity, used as a simple brightness measure.
\end{itemize}

In addition, the existing instance annotations were used to derive basic
geometry statistics, including the approximate button size in pixels, the
relative image area occupied by button instances, and the normalized button
location within the image. These geometry measurements were used to check
whether the training set covered a realistic range of viewing distances and
camera framing conditions.

The quantitative indicators were not used as automatic pruning rules. Instead,
images with low sharpness values, very dark appearance, or unusual geometric
properties were manually reviewed. In addition, a model-assisted assessment was
run over the full training split using a baseline instance-segmentation model.
For every training image, the model produced per-image mean \gls{iou},
false-positive count, and false-negative count. These metrics were used to
identify the lowest-\gls{iou} and highest-error cases for manual inspection.
The model-assisted pass therefore covered the complete training set, while the
manual review focused on the most difficult cases highlighted by these
per-image metrics. The descriptive outcomes of this assessment are reported in
Section~\ref{sec:dataset_quality_results}.


\section{Model architectures and training strategy}

Three model families are employed in this project, each serving a distinct role
within the overall perception pipeline. \gls{maskrcnn} is used as an
annotation-support model in the semi-automatic labeling workflow,
\gls{yolo}v8s segmentation is trained and evaluated as the deployment-oriented instance
segmentation model, and the \gls{ocr} recognizer is used for semantic
interpretation of the detected button crops.

\subsection{Experimental hardware and software environment}

All models training experiments reported in this thesis were executed
on the same workstation. The host system ran Ubuntu 22.04.5 LTS with Linux kernel
6.8.0-90. The machine was equipped with an AMD Ryzen 9 9950X 16-core processor and an NVIDIA GeForce RTX 4090 graphics card with
24~GiB of \gls{vram}. The training software environment used Python 3.10.12 and
PyTorch 2.5.1 compiled against \gls{cuda} 12.1. This configuration provided the
computational platform for the baseline training, hyperparameter tuning and the comparative evaluation runs discussed in Chapters~3 and~4.

\subsection{Common training strategy}

All trainable vision models were fine-tuned from pretrained weights rather than
trained from scratch, and their task-specific output heads were adapted to the
project datasets. For transfer learning, \gls{yolo}v8-Seg was initialized from
the official Ultralytics \texttt{yolov8s-seg.pt} checkpoint pretrained on
\gls{coco} for instance segmentation, \gls{maskrcnn} from Torchvision's default
\gls{coco}-pretrained \texttt{MaskRCNN\_ResNet50\_FPN} weights, and the \gls{ocr}
recognizer from the official PaddleOCR \texttt{PP-OCRv5\_mobile\_rec}
pretrained recognition checkpoint. Across the experiments, the train/validation
split was used for model fitting and model selection, while the held-out test
split was reserved for final comparison only.

\subsection{Mask R-CNN training}

\gls{maskrcnn} was used only as an annotation-support model within the
semi-automatic \gls{cvat} workflow. It was trained on \gls{coco}-formatted
instance annotations and retrained iteratively as the annotated dataset grew
from an initial manually labeled seed set to later larger annotation rounds.
After each retraining stage, the best validation checkpoint was exported back to
the \gls{cvat}--Nuclio pipeline so that automatic mask proposals for later
images started from a stronger model and required less manual correction. The
checkpoint progression and held-out reference comparison are summarized in
Appendix~\ref{app:maskrcnn_checkpoints}, since only the role of
\gls{maskrcnn} in the annotation workflow is relevant to the main methodology.

\subsection{YOLOv8s segmentation training}

The common training strategy was applied to the deployment-oriented \gls{yolo}v8s segmentation model using the Ultralytics framework \citep{ultralyticsdocs2026}. The initial baseline configuration was
scheduled for up to 100 epochs with an input resolution of $640 \times 640$, dynamic batch sizing
(\texttt{batch=-1}), warmup over 5 epochs, and early stopping patience
of 10 epochs. The augmentation policy followed the standard Ultralytics recipe used
throughout this study, including small geometric transformations,
horizontal flipping, and mosaic augmentation.

Although this baseline produced strong results, its training settings were selected
empirically. A structured hyperparameter tuning procedure was therefore conducted
to determine whether performance could be improved in a more systematic and
reproducible way. All tuning runs were logged and tracked in \gls{wandb}, which was
used to store the hyperparameter configurations, training curves, and validation
metrics of individual experiments.

The baseline settings were chosen as a pragmatic starting point. The
$640 \times 640$ input size balanced preservation of small-button detail against
the training and inference costs expected for embedded deployment, although
lower resolution can make small or distant button instances harder to localize
accurately. Dynamic batch sizing, warmup, and early stopping were used to
stabilize optimization and use the available \gls{gpu} memory efficiently.

Table~\ref{tab:yolo_hparam_tuning}. The table is intended to provide a compact

\subsection{Loss functions and optimization objectives}

Both instance-segmentation models were optimized with composite losses that
jointly account for classification, localization, and mask prediction.


\noindent\textbf{Mask R-CNN.}
The training objective of \gls{maskrcnn} is defined as a multi-task loss composed of
three terms \citep{he2017maskrcnn}:
\begin{equation}
\mathcal{L}_{\text{Mask R-CNN}} =
\mathcal{L}_{\text{cls}} +
\mathcal{L}_{\text{box}} +
\mathcal{L}_{\text{mask}},
\end{equation}
where $\mathcal{L}_{\text{cls}}$ denotes the classification loss, implemented as
categorical cross-entropy; $\mathcal{L}_{\text{box}}$ represents bounding-box
regression using the smooth $L_1$ loss; and $\mathcal{L}_{\text{mask}}$ is a
pixel-wise binary cross-entropy loss applied to each predicted instance mask.


\noindent\textbf{YOLOv8s segmentation.}
\gls{yolo}v8s segmentation integrates detection and segmentation into a single-stage architecture.
For comparison with \gls{maskrcnn}, the following expression presents a
simplified conceptual decomposition of the YOLOv8 segmentation objective rather
than the exact Ultralytics implementation. Its purpose here is to highlight the
different role of weighted detection and segmentation terms in the single-stage
YOLO formulation \citep{jocher2023yolov8}:
\begin{equation}
\mathcal{L}_{\text{YOLO}} =
\lambda_{\text{cls}} \mathcal{L}_{\text{cls}} +
\lambda_{\text{box}} \mathcal{L}_{\text{box}} +
\lambda_{\text{seg}} \mathcal{L}_{\text{seg}},
\end{equation}
where $\mathcal{L}_{\text{seg}}$ represents the segmentation loss applied to the
predicted mask outputs, and the weighting coefficients $\lambda$ control the
relative contribution of each task during optimization.


\subsection{OCR-based button interpretation}

Following instance segmentation, detected button regions are passed to a
semantic interpretation stage. Segemnted button instances are cropped and processed by
an \gls{ocr}-based recognition module to extract character labels or symbols associated with each button. 
Because button localization is already solved upstream by
the segmentation model, the recognizer does not need to detect text in the full image and instead operates on tightly
bounded button crops. This reduces computational cost and enables the robot to
associate localized interaction points with their functional meaning during
downstream decision-making.


\noindent\textbf{Recognition model architecture.}
For cropped-button recognition, a lightweight \gls{ocr} recognizer based on
\gls{paddleocr} \citep{paddleocrdocs2026} was selected. This model was preferred because it is
designed for efficient deployment and already provides a compact recognition
backbone suitable for embedded hardware. 
Only the recognition component of the \gls{ocr} stack was used. The detection component
of \gls{paddleocr} was intentionally omitted from the final recognition pipeline, because
button localization was already solved upstream by the instance segmentation model.
This avoids redundant computation and makes the \gls{ocr} stage conceptually cleaner:
segmentation localizes the button instance, and \gls{ocr} interprets that localized
instance.


\noindent\textbf{Fine-tuning strategy.}
The recognizer was initialized from the official pretrained English
\texttt{PP-OCRv5\_mobile\_rec} weights and fine-tuned on the project-specific crop
dataset described in Section~\ref{sec:dataset_selection}. During training, each crop was resized to the fixed input resolution of
$48 \times 320$ defined in the \gls{paddleocr} recognition configuration so that all
samples reached the network with a consistent image height and width.
Optimization used Adam with cosine learning-rate scheduling, warmup, and L2
regularization. Recognition-specific augmentation and multiscale sampling were
enabled to improve robustness and reduce overfitting to a single visual
presentation of the button crops.

The implementation followed the standard \gls{paddleocr} training workflow
\citep{paddleocrdocs2026}, using the official \texttt{tools/train.py} and
\texttt{tools/eval.py} scripts with project-specific \gls{yaml} configuration
files.

The \gls{ocr} tuning procedure is summarized in Table~\ref{tab:ocr_hparam_tuning}.
Stage 1 was used to determine an appropriate epoch budget, while Stage 2 fixed
that budget and performed a narrow optimizer sweep. All \gls{ocr} tuning runs
were logged in \gls{wandb} so that training curves, hyperparameter choices, and
validation metrics could be compared systematically.

\section{Evaluation metrics}

The evaluation in this project follows the metric outputs of the training and
validation toolchains used in the experiments. \gls{yolo}-based segmentation is
reported with \gls{coco}-style box and mask metrics, while the \gls{ocr}
recognizer is reported with exact-match accuracy and normalized edit distance.
Validation dataset was used for model selection and tuning, and held-out test
dataset was reserved for final reporting. The \gls{maskrcnn} annotation-support
comparison is included only as supplementary material in
Appendix~\ref{app:maskrcnn_checkpoints}.

\subsection{YOLO segmentation evaluation}

The \gls{yolo} experiments report the standard Ultralytics/\gls{coco} validation
and test metrics for both bounding boxes and segmentation masks. The main metric
used for model selection is mask \glsentryshort{map}@[0.50:0.95]. This metric averages \gls{ap} over
\gls{iou} thresholds from 0.50 to 0.95 in increments of 0.05 and is the most
representative single indicator of segmentation quality. In addition,
\texttt{metrics/mAP50(M)} is reported to show performance at the less strict 0.50
\gls{iou} threshold. This reporting convention follows the standard COCO-style
Ultralytics metrics interface \citep{lin2014coco,ultralyticsdocs2026}.

\begin{equation}
\mathrm{Precision} = \frac{TP}{TP + FP}, \qquad
\mathrm{Recall} = \frac{TP}{TP + FN}
\end{equation}

\begin{equation}
\mathrm{mAP}_{50\text{:}95} = \frac{1}{10}\sum_{t \in \{0.50,0.55,\ldots,0.95\}} \mathrm{AP}_{t}
\end{equation}

The complete set of reported \gls{yolo} metrics in this report therefore includes
mask precision, mask recall, \texttt{mAP50(M)}, and \texttt{mAP50-95(M)}, together
with the corresponding box metrics \texttt{precision(B)}, \texttt{recall(B)},
\texttt{mAP50(B)}, and \texttt{mAP50-95(B)}. These additional values are retained
because they help explain the behavior of a model beyond a single summary number.
For example, precision and recall indicate whether a model tends to miss valid
instances or to produce false positives, while the box metrics make it possible
to distinguish localization quality from mask quality. However, when ranking
segmentation models in this report, mask \glsentryshort{map}@[0.50:0.95] remains
the primary comparison criterion.

\subsection{OCR evaluation}

The \gls{ocr} recognition models are evaluated using exact-match accuracy and
normalized edit distance. Exact-match accuracy is the fraction of button crops for
which the predicted label string matches the ground-truth label exactly after the
same normalization procedure is applied to both. This metric is strict and is
therefore suitable for the final semantic interpretation task, where predicting
\texttt{4} instead of \texttt{14}, or \texttt{OPE} instead of \texttt{OPEN}, must
be counted as an error.

\begin{equation}
\mathrm{Accuracy}_{\text{\glsentryshort{ocr}}} = \frac{N_{\text{correct}}}{N_{\text{total}}}
\end{equation}

where $N_{\text{correct}}$ is the number of exactly correct predictions and
$N_{\text{total}}$ is the total number of evaluated crops.

In addition to exact-match accuracy, normalized edit distance is used to quantify
how close an incorrect prediction is to the target string. This metric is derived
from the Levenshtein edit distance between prediction and target and is normalized
to the interval $[0,1]$, where 1 indicates a perfect match. Unlike exact-match
accuracy, normalized edit distance gives partial credit to near-correct
predictions, which is useful when analyzing \gls{ocr} behavior on short strings and icon
labels that are often confused by only one or two characters.

\begin{equation}
\mathrm{NED} = 1 - \frac{1}{N} \sum_{i=1}^{N}
\frac{d_{\text{edit}}(\hat{y}_i, y_i)}{\max(|\hat{y}_i|, |y_i|, 1)}
\end{equation}

where $\hat{y}_i$ is the predicted string, $y_i$ is the corresponding ground-truth
string, and $d_{\text{edit}}$ denotes the Levenshtein edit distance.

During \gls{ocr} tuning, validation accuracy was treated as the primary model-selection
metric, while normalized edit distance was used as a secondary quality indicator.
Final \gls{ocr} benchmarking was then performed on the held-out \gls{ocr} test split using the
official \gls{paddleocr} evaluation script with the same configuration family as
used during training \citep{paddleocrdocs2026}.

To enable real-time execution on embedded hardware, the trained models are
optimized and deployed on a \gls{jetson} Orin platform. This section corresponds
to the deployment branch of the overall workflow-and-architecture overview
introduced in Figure~\ref{fig:scalable_workflow}. The deployment workflow is designed to be
identical for both the instance segmentation model and the \gls{ocr}-based
button classification model.

Models are first trained in PyTorch, exported to the Open Neural Network Exchange
(\gls{onnx}) \citep{onnx2019} format, and then converted on the \gls{jetson} Orin
device into optimized \gls{tensorrt} engines. Engine generation was performed
directly on the target hardware to ensure compatibility with the device-specific
\gls{gpu} architecture. \gls{fp16} precision was used to reduce memory footprint
and improve inference speed.

The final \gls{tensorrt}
\texttt{.engine} models were validated directly on the target device by running
them on a subset of held-out test images and checking that the predictions were
numerically sensible and visually consistent with the trained desktop models.

The resulting \gls{tensorrt} engines are integrated into \gls{ros} nodes responsible for
perception tasks. At runtime, image data from the \gls{rgbd} camera is passed through
the \gls{ros} pipeline and processed by the \gls{tensorrt} engines to produce instance
segmentation masks and corresponding button labels.

The complete deployment and optimization workflow is illustrated in
Figure~\ref{fig:tensorrt_workflow}. This approach ensures a consistent and efficient
deployment pipeline and enables fair evaluation of different model architectures
under identical runtime constraints.

\section{ROS pipeline architecture}

After deployment-oriented model selection, the \gls{tensorrt} engines were integrated into
a modular \gls{ros} pipeline on the target robot computer. This stage links
the trained perception models to live camera input, downstream message passing, and
deployment data collection.

\subsection{Deployment platform}

The runtime pipeline was executed on an \gls{jetson} Orin Nano running Ubuntu
22.04.5 LTS and \gls{ros} Humble. The device used JetPack~6.2.1,
corresponding to NVIDIA Linux for Tegra release \texttt{R36.4.7} with Linux
kernel \texttt{5.15.148-tegra}. \gls{tensorrt}~10.7.0 was used for optimized
inference. Visual input was provided by a Stereolabs ZED X \gls{rgbd} camera
connected through a ZED Link Duo capture card, using ZED SDK~5.2.1.

\subsection{Node responsibilities and outputs}

The deployed pipeline consists of the ZED camera driver, a \gls{yolo} inference
node, an \gls{ocr} inference node, and an \gls{adc}. As illustrated in
Figure~\ref{fig:ros2_runtime_architecture}, the camera provides the colour image,
registered depth image, and calibration data required for geometric perception.
The \texttt{yolo\_engine\_node} converts these inputs into button candidates that
already include image-plane localization through a mask and bounding box, a
representative center pixel, and a depth-based camera-relative target estimate.
The \texttt{ocr\_trt\_node} then adds
semantic information by assigning the recognized button text and its confidence
to each accepted candidate. Finally, the \gls{adc} receives the enriched button
candidates together with the camera image and stores only those samples that pass
the deployment quality gates.

The split-node design was chosen deliberately. Earlier experiments showed that
placing \gls{yolo} and \gls{ocr} \gls{tensorrt} inference in a single Python process increased the
risk of \gls{cuda}-context conflicts and made the system harder to debug. Separating the
geometric perception stage from the semantic recognition stage improved modularity
and allowed both runtime components to be benchmarked independently. In
Figure~\ref{fig:ros2_runtime_architecture}, the gray boxes denote \gls{ros} topics, whereas
the white boxes denote processing nodes or terminal outputs. The abbreviations

\subsection{Distance estimation and collector design}

The internal interface between the perception nodes is a custom \gls{ros}
button-target message, defined for this project to bundle the geometric output
of the \gls{yolo} stage and, after the \gls{ocr} step, the recognized button
text and text score. Image topics use a
best-effort, keep-last quality-of-service policy so that the pipeline
prioritizes the newest available camera frames. In practice, occasional frame
drops are acceptable because processing delayed images would be less useful than
continuing with recent sensor data.

Within the \texttt{yolo\_engine\_node}, target depth is estimated only from valid
depth pixels that fall inside the predicted segmentation mask. Let $\mathcal{V}$
denote the set of valid masked depth pixels after finite-value filtering, depth
range filtering, and the minimum-valid-pixel test. The representative target depth
is then computed as
\begin{equation}
z = \mathrm{Percentile}\left(\{d(i,j)\mid (i,j)\in \mathcal{V}\},\, p\right),
\end{equation}
where $p$ is the configured depth percentile. In the current implementation,
$p=50$ is used, corresponding to the median of the valid masked depth samples.
Using a percentile-based estimate rather than a plain mean reduces sensitivity to
outliers caused by missing returns and reflective elevator surfaces.

The representative image location is also derived from the valid masked depth
pixels. Here, $i$ denotes the image row index and $j$ denotes the image column
index in the depth image. In the current implementation, the pixel coordinates
are taken as the median valid depth location:
\begin{equation}
u = \mathrm{median}\left(\{j \mid (i,j)\in \mathcal{V}\}\right), \qquad
v = \mathrm{median}\left(\{i \mid (i,j)\in \mathcal{V}\}\right).
\end{equation}

If the camera intrinsics are given by focal lengths $(f_x,f_y)$ and principal
point $(c_x,c_y)$, the 3D target position in the camera optical frame is computed
as
\begin{equation}
x = \frac{(u-c_x)z}{f_x}, \qquad
y = \frac{(v-c_y)z}{f_y}.
\end{equation}
This projection step provides the button target that can be used by downstream robotic
modules and by the \gls{adc}.

To support iterative improvement after deployment, the \gls{adc} stores
selected images and annotations in a \gls{coco}-compatible structure. Sample export
is not performed for every frame. Instead, frames pass a sequence of quality gates
before they are written to a dataset session. The threshold values for image
brightness, image sharpness, and minimum visible button size were derived from the
dataset quality assessment in Section~\ref{sec:dataset_quality_results}, where the
observed brightness, blur, and button-size distributions were analyzed to define
practical acceptance ranges for deployment collection. At image level, the collector
therefore applies brightness and sharpness checks, while at target level it applies
minimum score and size thresholds, followed by temporal stability checks and
duplicate rejection.
